# Does an accessibility-derived observation layer beat a screenshot loop?

**Short answer: partly, and not where the hypothesis predicted.** The tool
eliminates visual grounding failure entirely and cuts image tokens by ~7×, but
it does not improve success rate, does not reduce the number of model calls,
and whether it is cheaper depends on which budget you measure. Crop-priority
(B) and text-priority (C) are indistinguishable on every metric measured,
including on the non-textual tasks built specifically to separate them.

All figures below come from `RESULTS.md`, generated by `analysis/aggregate.py`
from `results/raw/main.jsonl`. 126 runs, 0 excluded. Intervals are 95 %
bootstrap percentile intervals over runs.

---

## 1. What was measured

Three observation channels, everything else held constant — same model
(Claude Sonnet), same system-prompt skeleton, same 14 tasks, same step limits,
same executor, same debounce, same seeds, same deterministic reset, arms
interleaved so any drift hit all three equally.

| Arm | Start of task | Each step | Action |
|---|---|---|---|
| **A** baseline | task + full screenshot | full screenshot, **replacing** the previous one | pixel coordinates |
| **B** crop-priority | task + full element table + anchor screenshot | verb delta + labelled pixel crop of every changed region | element id |
| **C** text-priority | same as B | verb delta, text only; crop only where the tree cannot describe the change | element id |

14 tasks × 3 arms × 3 repetitions = 126 runs. Every task ends in a
programmatic check of final state — file bytes, CSV contents, page state read
over CDP. No model judged success anywhere.

Total measured API spend on the experiment: **$6.71** of the $40 budget.

## 2. Results

### 2.1 The headline: no difference in what the agent achieves

| | A (baseline) | B (crop-priority) | C (text-priority) |
|---|---|---|---|
| Success rate | 0.810 [0.690, 0.929] | 0.786 [0.667, 0.905] | 0.810 [0.690, 0.929] |
| Steps / task | 7.3 [6.2, 8.6] | 9.6 [8.2, 11.1] | 9.3 [7.8, 10.9] |
| Model calls / completed task | 9.0 | 12.2 | 11.5 |
| Cost / task (USD) | 0.0602 [0.0464, 0.0757] | 0.0507 [0.0371, 0.0658] | 0.0488 [0.0335, 0.0663] |

Success rate, model calls, steps and cost **all overlap**. On the metric the
design document names as primary — *model calls per completed task* — the
baseline is nominally best (9.0 vs 12.2 and 11.5), though the intervals
overlap and no winner can be declared at this N.

This is a negative result on the central claim, and it is the most important
line in this report.

### 2.2 Where the tool wins decisively

Two effects separate cleanly, with non-overlapping intervals:

**Grounding failure is eliminated, not reduced.**

| | A | B | C |
|---|---|---|---|
| Grounding failures / task | 0.31 [0.10, 0.55] | **0.00** | **0.00** |
| Runs with ≥1 grounding failure | 14.3 % | **0 %** | **0 %** |

A "grounding failure" here is a click that landed on no element at all. For
arms B and C this is not merely rare, it is structurally impossible: the agent
selects an id from a list and the coordinates come from the operating system.
The design document's claim that "ese error no se reduce: deja de ser posible"
is confirmed exactly.

**Image tokens drop ~7×.**

| | A | B | C |
|---|---|---|---|
| Image tokens / task | 8,976 [7,602, 10,526] | 1,322 [1,292, 1,357] | 1,287 [1,231, 1,370] |

B is 6.79× cheaper in pixels than A, C is 6.97× cheaper. Both separated.

**The cache behaves exactly as the append-only design predicts.**

| | A | B | C |
|---|---|---|---|
| Cache hit share | 20.8 % | **91.0 %** | **91.9 %** |
| TTFT / step (ms) | 1,316 [1,247, 1,393] | 934 [886, 982] | 884 [837, 935] |

The baseline replaces its screenshot each step, which invalidates the prefix;
the tool arms append and reuse it. That shows up directly in time-to-first-token:
the baseline is ~400 ms slower per step to start producing, which validates
the append-only design on its own terms.

### 2.3 The surprise: raw token count runs the other way

| | A | B | C |
|---|---|---|---|
| Total tokens / task | **17,816 [14,896, 21,155]** | 75,389 [51,850, 102,595] | 74,515 [48,559, 102,400] |
| Observation tokens / task | 969 [724, 1,265] | 4,489 [2,924, 6,277] | 4,164 [2,627, 5,869] |
| Cache-read tokens / task | 3,608 | 67,646 | 67,389 |

The baseline uses **4.2× fewer total tokens**, separated. The design document
predicted the opposite (~15k for the tool vs ~50k for the standard loop).

The mechanism is straightforward once the numbers are in front of you. The
tool arms pay a large one-off element table (the initial observation is
thousands of text tokens where the baseline's is a few hundred), and then
*never discard it*: an append-only context is re-read in full on every
subsequent step, so cache-read tokens accumulate roughly quadratically in step
count. The baseline's rebuilt context stays short — one screenshot and a
history summary — so its total stays flat.

Note what this does **not** mean. Cache reads are billed at roughly a tenth of
fresh input, so a 4.2× token disadvantage does not translate into a 4.2× cost
disadvantage; cost overlaps. The raw token total conflates cheap and expensive
tokens, which matters enormously for the next section.

### 2.4 Equal-budget comparison: the answer depends on the measure

The brief asks for success rate at equal token budget, letting the cheaper arm
spend its surplus on extra steps. Running that comparison three ways shows the
conclusion inverting depending on what is held equal.

**(a) Budget on raw total tokens — baseline wins**

| Budget | A | B | C |
|---|---|---|---|
| 15,000 | **57.1 %** | 28.6 % | 33.3 % |
| 30,000 | **81.0 %** | 40.5 % | 42.9 % |
| 60,000 | 81.0 % | 66.7 % | 66.7 % |

**(b) Budget on fresh tokens (input + cache-write + output) — tool wins**

| Budget | A | B | C |
|---|---|---|---|
| 4,000 | 19.0 % | 40.5 % | **50.0 %** |
| 8,000 | 28.6 % | 61.9 % | **66.7 %** |
| 15,000 | 61.9 % | **76.2 %** | **76.2 %** |
| 30,000 | 81.0 % | 78.6 % | 81.0 % |

**(c) Budget on money — tool wins at tight budgets, converges when loosened**

| Budget | A | B | C |
|---|---|---|---|
| $0.02 | 19.0 % | 38.1 % | **45.2 %** |
| $0.04 | 42.9 % | 57.1 % | **64.3 %** |
| $0.06 | 61.9 % | 64.3 % | **71.4 %** |
| $0.10 | **81.0 %** | 76.2 % | 76.2 % |

Under a tight cost budget the tool arms complete roughly twice as many tasks
as the baseline ($0.02: 45 % for C vs 19 % for A). Under a loose one the
advantage disappears and the baseline pulls level. Budgeting on raw tokens
reverses the finding entirely, because it charges the append-only arms full
price for tokens the provider served from cache.

**Caveat on rigour:** this is a *post-hoc* reclassification of the main runs,
not a fresh sweep in which each arm was given the budget and allowed extra
steps to use it. The harness supports the proper version
(`--token-budget` with `--step-mult`) but it was not run — see §4.

### 2.5 B versus C: no difference, including where there should be one

Every metric overlaps: success (0.786 vs 0.810), steps (9.6 vs 9.3), model
calls, cost, image tokens (1,322 vs 1,287), grounding failures (both zero).

The three non-textual tasks existed precisely to separate them, and did not:

| Group | Arm | Success | Image tokens | Steps |
|---|---|---|---|---|
| non-textual | A | 1.000 | 4,912 | 4.0 |
| non-textual | B | 1.000 | 1,228 | 4.0 |
| non-textual | C | 1.000 | 1,228 | 4.0 |

All three arms scored 3/3 on all three visual tasks in exactly 4 steps.
**The reason is a flaw in the task design, not a finding about the arms.**
Both B and C receive the anchor screenshot at step 0, and all three visual
tasks are answerable from that first image alone: look at the chart, read off
the tallest bar, type it, submit. The per-step delta — the only place B and C
differ — never carried decisive information, so B's crops were never load-bearing.
Note that B and C emitted an *identical* 1,228 image tokens, i.e. the anchor and
nothing else: on these tasks arm B never triggered a single crop.

To separate B from C, a task must require *noticing a visual change mid-task*:
a progress bar completing, a button greying out, a chart redrawing after a
filter is applied. No such task is in this suite. This is the single biggest
gap in the experiment.

### 2.6 Task-level notes

Two tasks failed 0/3 on **all three arms**, so they contribute nothing to arm
comparison and drag every success rate down equally:

- `calc_total` — requires computing a total in a cell *and* a Save-As to CSV
  through LibreOffice's multi-step dialog with a format-confirmation modal.
- `cross_report_summary` — read two figures in one app, create a new file in
  another; every run hit the 18-step limit.

Excluding them would raise all three arms' success rates by roughly the same
amount and would not change any comparison. They are retained because
excluding tasks after seeing results is exactly the kind of choice that
manufactures conclusions.

`files_rename` is the one task where the baseline visibly beat the tool arms:
A 3/3 in 6.0 steps, B and C 2/3 in 16.0 steps. Both tool arms exhausted their
step budget navigating the file manager's context menu, which suggests the
element table for pcmanfm's popup menus is less usable than a screenshot.
Worth investigating; not investigated here.

## 3. The three questions, answered

### Does the tool (B or C) beat the baseline (A)? On which metric, and by how much?

**On grounding and pixels, decisively. On task outcome and cost, no.**

- **Grounding failures: 0.31/task → 0.00/task.** Separated. Structurally
  eliminated, not merely reduced.
- **Image tokens: 6.8–7.0× fewer.** Separated.
- **TTFT: 1,316 ms → ~900 ms per step**, a ~30 % reduction, from the preserved
  cache. Separated.
- **Success rate: 0.810 vs 0.786/0.810.** No detectable difference.
- **Model calls per task: 7.3 vs 9.6/9.3**, nominally favouring the baseline.
  No detectable difference.
- **Cost per task: $0.060 vs $0.051/$0.049**, nominally favouring the tool.
  No detectable difference.
- **Total tokens: 4.2× *more* for the tool.** Separated, against the
  hypothesis.

At an equal *cost* budget of $0.02–0.06 per task the tool arms complete
1.2–2.4× as many tasks; at $0.10 the advantage is gone.

### Does B beat C — do the crops earn their extra tokens?

**No difference detectable on any metric, and the tasks that should have
decided it could not.** B and C differ by 35 image tokens per task on average
(1,322 vs 1,287) — the crop mechanism barely fired, because the tasks in this
suite are dominated by textual changes that the tree already describes
literally, which is precisely the one case the specification says needs no
crop. On the three non-textual tasks B emitted zero crops.

The honest conclusion is not "crops don't help" but **"this experiment could
not test the question"**. The measurement it does support is narrower: on a
suite of ordinary desktop tasks, crop-priority costs essentially nothing extra
over text-priority (+2.7 % image tokens, overlapping) and buys nothing
measurable either.

### Where does the advantage come from — the table, the deltas, or the cache?

**Partially answerable, because arm D was not run.**

What the data supports:

- **The cache is real and measurable.** 91 % hit rate for B/C versus 21 % for
  A, and a ~400 ms/step TTFT reduction that tracks it directly. This is
  attributable to the append-only design, since it is the only thing that
  differs in how the context is maintained.
- **The table is what eliminates grounding failure.** Nothing else can explain
  0.31 → 0.00, because the delta mechanism does not touch how an action is
  addressed; the id-addressed action does.
- **"Only send what changed" cannot be isolated.** Separating the table's
  contribution from the delta's contribution is exactly what arm D exists for,
  and arm D was not run (DECISIONS D4.7). What the data does show is that
  sending only deltas did **not** deliver the token reduction it was supposed
  to, because the retained context outgrows the per-step saving.

## 4. Threats to validity

**N is small and the study is underpowered.** 3 repetitions per (task, arm),
42 runs per arm. Most comparisons come back "no difference detectable", and
that phrase means *underpowered*, not *equal*. A success-rate gap of under
~15 points could not be detected here. The brief permits 3 reps under budget
pressure and this run used that allowance.

**The non-textual tasks do not test what they were built to test.** All three
are solvable from the anchor screenshot alone, so the B/C distinction was
never exercised (§2.5). Any claim about crop-priority from this data is
unsupported.

**Two of fourteen tasks failed universally.** `calc_total` and
`cross_report_summary` scored 0/42 across all arms, so 14 % of the suite
contributes only noise and depresses all success rates equally.

**The equal-budget comparison is post-hoc.** §2.4 reclassifies completed runs
rather than re-running each arm under an enforced budget with a raised step
ceiling. A true equal-budget run could differ, particularly for the tool arms,
which would be able to convert their cost surplus into more steps.

**Temperature is not pinned.** The CLI exposes no temperature control, so
decoding settings are identical across arms by construction but are not 0.
Run-to-run variance is therefore larger than it needs to be, which widens
every interval and makes the underpowering worse.

**The model channel is the `claude` CLI, not the raw API.** Every call carries
~1.1 k tokens of residual harness prompt. It is identical across arms so it
cannot bias the comparison, but it inflates absolute token and cost figures,
and it compresses relative differences (a fixed cost added to both sides of
every ratio).

**Arm A was reimplemented mid-experiment and its first 14 runs discarded.**
The first version accumulated screenshots in an append-only context, giving
the baseline caching the standard loop does not have. The discarded runs are
archived in `results/raw/discarded_armA_v1.jsonl` and excluded from every
figure here. The corrected baseline is the one reported; if the reimplementation
is wrong in some way I have not seen, every A figure moves.

**Arm A's history is textual.** The corrected baseline shows one screenshot
plus a text summary of prior actions. A baseline that retained the last 2–3
screenshots would be a different, arguably stronger, configuration and was not
measured.

**Wall-clock and spend budgets are reported against time worked.** The session
was rate-limited and idle for ~6 hours mid-build (06:15–12:20 UTC); elapsed
wall clock from first command to final report is ~10 h, of which ~4 h was time
actually working (DECISIONS D4.1). The 126-run sweep itself ran 12:33–14:10
UTC. Spend was $6.71 of $40, so the
experiment stopped for reasons of wall clock and scope, not money — with more
time the right move would have been more repetitions, not more tasks.

**Uncovered changed regions are not detected.** Arm C's forced-crop rule fires
on visual roles and on a failed bbox-honesty check, but not on "a region
changed with no tree element behind it" (DECISIONS D4.8). This biases against
C only in situations this suite does not contain.

**Single environment, single model, single session.** One container, one
model, one provider, one afternoon. Nothing here speaks to other toolkits
(Electron and Qt are untested), other models, or applications with a poorer
accessibility tree — and the coverage question that governs the whole
economics of the approach (§6.3 of the design document) was not measured at
all.

## 5. What I would do next, in order

1. **Build tasks that actually separate B from C**: a mid-task visual change
   the tree cannot describe — a progress bar reaching 100 %, a control greying
   out, a chart redrawing after a filter. Without these the crop question is
   open.
2. **Run arm D.** It is implemented and it is the only way to split "having
   the table" from "sending only the delta".
3. **Fix the delta arms' context growth.** The measured 4.2× token
   disadvantage comes from never discarding the accumulated context. The
   compaction and crop-ageing the design document specifies are the intended
   remedy and were not exercised — tasks were too short to trigger them.
4. **Raise N to 10+ per cell and pin temperature** before making any claim
   about success rate.
5. **Run the equal-budget sweep properly**, enforcing the budget during the
   run with a raised step ceiling.

---

## 6. Summary

The observation layer does exactly what its design says it does at the
mechanical level: it makes visual grounding failure impossible, it cuts pixel
traffic by ~7×, and it preserves the prefix cache (91 % vs 21 %), which shows
up as ~400 ms/step less time-to-first-token.

What it does not do, in this experiment, is make the agent better or clearly
cheaper. Success rate is flat. Model calls per task — the metric the design
document names as the one that matters — is nominally worse. And the
"send only what changed" mechanism *increased* total tokens 4.2×, because an
append-only context that is never compacted costs more to re-read than a short
context costs to rebuild.

The most useful number for someone deciding whether to build this: under a
tight cost budget the tool completes roughly twice as many tasks as the
screenshot loop; under a loose one, neither is measurably better. Which of
those regimes you are in should decide the question — and that is a narrower,
more contingent claim than the hypothesis this experiment set out to confirm.
