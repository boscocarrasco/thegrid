# Does an accessibility-derived observation layer beat a screenshot loop?

**Short answer: it wins decisively on two mechanisms and on cost-constrained
throughput, and not at all on unconstrained task success.** The tool makes
visual grounding failure structurally impossible (0.27 → 0.00 failures per
task), cuts image tokens ~6.5×, and holds a 91 % prefix-cache hit rate against
the baseline's 22 %, worth ~380 ms/step of time-to-first-token. It does *not*
improve success rate when tokens are free, and it does not reduce the number
of model calls.

Two results deserve to be read before anything else:

- **Crop-priority (B) beats text-priority (C) exactly where the design says it
  should, and by the maximum possible margin: 6/6 versus 0/6.** When the
  decisive fact appears mid-task and is carried only by appearance, the
  text-only delta is blind to it — and it costs B only 110 image tokens per
  task to see it.
- **"Only send what changed" is the load-bearing part, not the element table.**
  Arm D (table + full screenshot, no deltas) matches the baseline's success
  rate at **2.6× the cost per completed task**, making it the worst arm
  measured.

All figures come from `RESULTS.md`, generated by `analysis/aggregate.py` from
`results/raw/*.jsonl`. 192 runs, 0 excluded. Intervals are 95 % bootstrap
percentile intervals over runs.

---

## 1. What was measured

Four observation channels, everything else held constant — same model (Claude
Sonnet), same system-prompt skeleton, same tasks, same step limits, same
executor, same debounce, same seeds, same deterministic reset, arms
interleaved so any drift hit all of them equally. `arms/channels.py` is the
entire independent variable.

| Arm | Start of task | Each step | Action |
|---|---|---|---|
| **A** baseline | task + full screenshot | full screenshot, **replacing** the previous one | pixel coordinates |
| **B** crop-priority | task + full element table + anchor screenshot | verb delta + labelled pixel crop of every changed region | element id |
| **C** text-priority | same as B | verb delta, text only; crop only where the tree cannot describe the change | element id |
| **D** ablation | same as B | full table + full screenshot, **no deltas** | element id |

16 tasks × 4 arms × 3 repetitions = 192 runs. Every task ends in a
programmatic check of final state — file bytes, CSV contents, page state read
over CDP. No model judged success anywhere.

Total measured API spend: **$14.72** of the $40 budget.

## 2. Results

### 2.1 Headline

| | A (baseline) | B (crop-priority) | C (text-priority) | D (table+shot) |
|---|---|---|---|---|
| Success rate | 0.896 [0.812, 0.979] | 0.875 [0.771, 0.958] | 0.771 [0.646, 0.875] | 0.875 [0.771, 0.958] |
| Steps / task | 7.0 [6.0, 8.1] | 9.0 [7.8, 10.4] | 9.6 [8.2, 11.0] | 8.3 [7.0, 9.6] |
| Model calls / completed task | 7.8 | 10.3 | 12.5 | 9.5 |
| Cost / completed task (USD) | 0.0633 | **0.0529** | 0.0781 | 0.1640 |
| Total tokens / task | **17,068** | 68,610 | 80,861 | 182,855 |

With tokens unconstrained, **all four success rates overlap** except that C is
nominally lowest. On the design document's primary metric — model calls per
completed task — the baseline is nominally best. Neither difference is
detectable at this N.

That is a negative result on the central claim as usually stated, and §2.4
shows why it is also the wrong way to pose the question.

### 2.2 Where the tool wins decisively

Three effects separate cleanly.

**Grounding failure is eliminated, not reduced.**

| | A | B | C | D |
|---|---|---|---|---|
| Grounding failures / task | 0.27 [0.08, 0.48] | **0.00** | **0.00** | **0.00** |
| Runs with ≥1 grounding failure | 12.5 % | **0 %** | **0 %** | **0 %** |

A grounding failure here is a click that landed on no element at all. For the
id-addressed arms this is not merely rare but impossible by construction: the
agent picks an id and the coordinates come from the operating system. The
design document's claim — *"ese error no se reduce: deja de ser posible"* — is
confirmed exactly.

The act-time validation counter shows the other side of the same coin: C and D
abort 0.08 and 0.12 actions per task respectively, catching cases where the
element moved or vanished between the model deciding and the executor acting.
Those are failures the baseline cannot even detect; it just clicks.

**Image tokens drop ~6.5×.**

| | A | B | C | D |
|---|---|---|---|---|
| Image tokens / task | 8,622 [7,368, 10,003] | 1,324 [1,298, 1,354] | 1,280 [1,231, 1,352] | 10,157 [8,647, 11,768] |

**The append-only design does what it claims to the cache.**

| | A | B | C | D |
|---|---|---|---|---|
| Cache hit share | 22.1 % | **91.0 %** | **91.2 %** | 85.7 % |
| TTFT / step (ms) | 1,297 [1,233, 1,367] | **924 [881, 969]** | **913 [866, 964]** | 1,006 [956, 1,057] |

The baseline replaces its screenshot each step, which invalidates the prefix;
the tool arms append and reuse it. That shows up directly as ~384 ms/step less
time-to-first-token, separated. The append-only design is validated on its own
terms.

### 2.3 The surprise: raw token count runs the other way

The baseline uses **4.0× fewer total tokens** than B and 4.7× fewer than C —
separated, and the opposite of the design document's prediction (~15 k for the
tool vs ~50 k for the standard loop).

The mechanism: the tool arms pay a large one-off element table and then never
discard it. An append-only context is re-read in full every step, so cache-read
tokens accumulate roughly quadratically in step count (B: 61,552 cache-read
tokens per task). The baseline's rebuilt context stays short — one screenshot
plus a text history — so its total stays flat.

This does *not* translate into a 4× cost disadvantage, because cache reads bill
at roughly a tenth of fresh input: B is in fact the **cheapest** arm per
completed task ($0.0529 vs A's $0.0633). But it means the compaction and
crop-ageing the design document specifies are not optional niceties — they are
the difference between the delta mechanism paying off and quietly not. Tasks
here were too short (7–10 steps) to trigger either, so neither was exercised.

### 2.4 Equal budget: the answer depends on what you hold equal

The brief asks for success at equal token budget. Running it three ways shows
the conclusion inverting with the measure — which is itself the finding.

**(a) Budget on raw total tokens — baseline wins**

| Budget | A | B | C | D |
|---|---|---|---|---|
| 15,000 | **62.5 %** | 25.0 % | 29.2 % | 0.0 % |
| 30,000 | **89.6 %** | 47.9 % | 37.5 % | 31.2 % |
| 60,000 | **89.6 %** | 70.8 % | 58.3 % | 50.0 % |

**(b) Budget on fresh tokens (input + cache-write + output) — B wins**

| Budget | A | B | C | D |
|---|---|---|---|---|
| 4,000 | 18.8 % | **45.8 %** | 43.8 % | 0.0 % |
| 8,000 | 33.3 % | **66.7 %** | 58.3 % | 31.2 % |
| 15,000 | 70.8 % | **79.2 %** | 66.7 % | 52.1 % |
| 30,000 | **89.6 %** | 87.5 % | 77.1 % | 72.9 % |

**(c) Budget on money — B wins at tight budgets, the baseline takes over as they loosen**

| Budget | A | B | C | D |
|---|---|---|---|---|
| $0.02 | 18.8 % | **43.8 %** | 39.6 % | 0.0 % |
| $0.04 | 45.8 % | **62.5 %** | 56.2 % | 31.2 % |
| $0.06 | **70.8 %** | 68.8 % | 62.5 % | 47.9 % |
| $0.10 | **89.6 %** | 79.2 % | 66.7 % | 66.7 % |

At $0.02 per task the tool completes 2.3× as many tasks as the baseline; by
$0.06 the baseline is level, and by $0.10 it is ten points ahead. Budgeting on raw tokens
reverses the finding entirely, because it charges the append-only arms full
price for tokens the provider served from cache. Anyone reporting a single
equal-budget number here is choosing their conclusion by choosing their
denominator.

**Caveat:** this is a *post-hoc* reclassification of completed runs, not a
fresh sweep with the budget enforced during the run and a raised step ceiling.
The harness supports the proper version (`--token-budget` with `--step-mult`);
it was not run.

### 2.5 B versus C: crops earn their keep, but only where appearance carries meaning

Pooled over all 16 tasks, B and C overlap on every metric (success 0.875 vs
0.771). Split by task type, the picture is completely different:

| Group | Arm | n | Success | Image tokens | Steps |
|---|---|---|---|---|---|
| **mid-task appearance change** | A | 6 | 1.000 | 6,140 | 5.0 |
| | **B** | 6 | **1.000** | **1,338** | **5.0** |
| | **C** | 6 | **0.000** | 1,228 | 11.5 |
| | D | 6 | 1.000 | 6,140 | 5.0 |
| non-textual but anchor-solvable | A | 9 | 1.000 | 4,912 | 4.0 |
| | B | 9 | 1.000 | 1,228 | 4.0 |
| | C | 9 | 1.000 | 1,228 | 4.0 |
| everything else | A | 33 | 0.848 | 10,084 | 8.2 |
| | B | 33 | 0.818 | 1,348 | 11.2 |
| | C | 33 | 0.848 | 1,303 | 10.8 |

The **mid-task appearance change** group (`vdelta_rows`, `vdelta_bars`) is the
one that tests the question. Both tasks put the decisive fact in an element
that *appears during the task* and whose meaning is carried only by
appearance: six list rows with ordinary names where one has a red background,
and five labelled bars where only pixel width says which is longest. The tree
reports the names and says nothing about colour or width.

- **B crops all six added rows and scores 6/6**, at a cost of 110 image tokens
  per task over C (1,338 vs 1,228, i.e. +9 % on this group and 1.8 % of
  what arm A spends on the same tasks).
- **C receives `+ added list item "job-delta"` and five identical siblings,
  and scores 0/6.** It also burns 11.5 steps against B's 5.0, clicking around
  trying to discover by interaction what a single crop would have shown.

This is the sharpest result in the experiment, and it is the design document's
own prediction: crop-priority costs +3.4 % image tokens against text-priority across
the whole suite and buys the ability to see anything the tree cannot describe.

The first three non-textual tasks I built (bar chart, filled-circle count,
colour badges) failed to test this at all: every arm scored 3/3 in 4 steps
because all three are answerable from the anchor screenshot alone, so arm B
emitted **zero** crops on them. That was a flaw in my task design, found by
inspecting why the groups were identical, and fixed by adding the two tasks
above. Both groups are reported separately rather than pooled.

### 2.6 Arm D: the table alone is not the mechanism

Arm D isolates "having the element table" from "sending only what changed". It
gets the full table *and* a full screenshot every step, with no deltas.

| | A | B | D |
|---|---|---|---|
| Success rate | 0.896 | 0.875 | 0.875 |
| Total tokens / task | 17,068 | 68,610 | **182,855** |
| Cost / completed task | $0.0633 | **$0.0529** | **$0.1640** |
| Grounding failures | 0.27 | 0.00 | 0.00 |

D is level with the baseline's success rate at **2.6× the cost per completed
task** and 3.1× B's — the most expensive arm by a wide margin. It inherits the table's
benefit (zero grounding failures) but, by re-sending the whole table and a
whole screenshot every step, it inherits neither the baseline's short context
nor the delta arms' small per-step payload.

D also produced the experiment's one interesting outlier: it is the only arm
that ever completed `cross_report_summary` (1/3 against 0/3 for A, B and C),
the hardest cross-application task. Having both the table and the picture
simultaneously appears to help on genuinely hard navigation — at a price no
one should want to pay routinely.

### 2.7 Task-level notes

One task fails on all four arms and contributes only noise:

- `cross_report_summary` — 1/12 (the single D success). Every other run hit
  the 18-step limit.

**`calc_total` was a second such task until the verifier itself was found to be
wrong.** It searched the saved CSV for the string `48.5`; the total the task
asks for is 1.5 + 3.25 + 7.0 = **11.75**, which no correct answer could ever
satisfy. Eleven of twelve runs wrote the right total, saved it as CSV exactly
as instructed, and were recorded as failures. The one genuine failure is a D
run that never created the file at all. The bug and the correction are set out
in DECISIONS D6.1; the corrected task scores A 3/3, B 3/3, C 3/3, D 2/3.

The correction was worth making rather than noting, because the earlier reading
of this task was not merely imprecise but backwards: the previous version of
this report explained the 0/12 as LibreOffice's Save-As dialog defeating every
arm. The agents cleared that dialog on eleven of twelve attempts. A verifier
that cannot be satisfied does not measure difficulty, it manufactures it — and
it took looking at what the runs actually wrote, not at their scores, to see it.

`files_rename` is the one task where the baseline beat the tool arms outright:
A 3/3 in 6.0 steps, B/C/D 2/3 in ~16 steps. All three tool arms exhausted
their step budget in the file manager's context menu, which suggests pcmanfm's
popup-menu representation in the tree is harder to navigate than a picture of
it. Not investigated further.

The failing task is retained. Dropping tasks after seeing which ones failed
is how results get manufactured.

## 3. The three questions, answered

### Does the tool (B or C) beat the baseline (A)? On which metric, and by how much?

**On grounding, pixels, cache and cost-constrained throughput: yes,
decisively. On unconstrained success rate and model calls: no.**

| Metric | A | best tool arm | verdict |
|---|---|---|---|
| Grounding failures / task | 0.27 | **0.00** (B, C, D) | separated — eliminated |
| Image tokens / task | 8,622 | **1,280** (C) | separated — 6.7× |
| TTFT / step | 1,297 ms | **913 ms** (C) | separated — 1.42× |
| Cache hit share | 22.1 % | **91.2 %** (C) | separated |
| Cost / completed task | $0.0633 | **$0.0529** (B) | overlapping |
| Success @ $0.02/task | 18.8 % | **43.8 %** (B) | 2.3× |
| Success (unconstrained) | 0.896 | 0.875 (B) | no difference detectable |
| Model calls / task | **7.0** | 9.0 (B) | no difference detectable |
| Total tokens / task | **17,068** | 68,610 (B) | separated — against the tool |

The honest summary: the tool changes *how* the agent fails and *what it costs
per unit of progress*, not *whether* it succeeds when money is no object.

### Does B beat C — do the crops earn their extra tokens?

**Yes, and the margin is total where it matters.** On the task class where the
decisive information is a mid-task appearance change, **B scores 6/6 and C
scores 0/6**, with C also taking 2.3× the steps. The extra cost of crop-priority
is 110 image tokens per task (1,338 vs 1,228): +9 % on this group,
+3.4 % across the whole suite.

Pooled across all tasks the two overlap (0.875 vs 0.771), because 14 of 16
tasks are dominated by textual changes the tree already describes literally —
precisely the one case the specification says needs no crop, where B correctly
emits nothing extra.

So the answer is conditional and cheap to act on: crops cost almost nothing on
ordinary tasks (+3.4 % image tokens suite-wide) because they rarely fire, and they are the difference between
working and not working when appearance carries meaning. Send them.

### Where does the advantage come from — the table, the deltas, or the cache?

Now separable, with arm D run.

- **The table is what eliminates grounding failure.** Every id-addressed arm
  (B, C, D) records exactly 0.00 grounding failures against the baseline's
  0.27. The delta mechanism cannot explain this — it does not touch how an
  action is addressed.
- **The deltas are what make it affordable.** D has the table and no deltas,
  and costs $0.1640 per completed task against B's $0.0529 — a **3.1×
  penalty** for that one difference. The table alone is not a win; the table
  plus "send only what changed" is.
- **The cache is real but secondary.** 91 % hit rate for B/C versus 22 % for
  A, worth ~380 ms/step of TTFT. It is a latency benefit, clearly attributable
  to the append-only design; but D also achieves 85.7 % and is still the most
  expensive arm, so cache retention alone does not deliver the economics.

Ranked: **deltas ≫ table > cache**, with the table supplying correctness
(grounding) and the deltas supplying economics.

## 4. Threats to validity

**N is small.** 3 repetitions per (task, arm), 48 runs per arm. Most pooled
comparisons return "no difference detectable", which means *underpowered*, not
*equal*: a success-rate gap under ~15 points could not be detected. The B-vs-C
result in §2.5 is exempt from this concern only because it is 6/6 against 0/6
— a complete separation — but it rests on **two tasks**, and two tasks is a
narrow base for a general claim.

**The vdelta tasks were designed after seeing that the first visual tasks
failed to discriminate.** They were built to make the B/C difference visible,
and they succeed at that by construction. They demonstrate that a real,
plausible task class exists where crop-priority is decisive; they do not
establish how common that class is in real work. That frequency is what
determines whether crops matter in practice, and it was not measured.

**One of sixteen tasks fails almost universally** (`cross_report_summary`
1/12), so ~6 % of the suite depresses all arms equally and contributes no
discriminating power.

**A verifier was wrong, and every success rate here is the corrected one.**
`calc_total` was scored against a total no correct answer produces, so eleven
runs that did the task properly were recorded as failures (DECISIONS D6.1).
The bug hit all four arms in proportion, so no comparison in this report
changes direction — but every absolute success rate rose by 4–6 points when it
was fixed, and the first version of this report published the wrong ones. The
correction is applied by `analysis/rescore.py` at analysis time, from the file
contents the broken verifier preserved inside its own failure message; the raw
JSONL is unedited and `--no-rescore` reproduces the original figures. What
should worry a reader is not this bug but the class it belongs to: nothing in
the harness checks that a verifier can be satisfied at all, so a second one
like it would look exactly like a hard task.

**The equal-budget comparison is post-hoc**, not a sweep with budgets enforced
during the run and extra steps allowed. The tool arms would likely gain most
from a proper version, since they have surplus to convert.

**Temperature is not pinned.** The CLI exposes no temperature control, so
decoding settings are identical across arms by construction but are not 0.
This widens every interval and makes the underpowering worse.

**The model channel is the `claude` CLI, not the raw API.** Every call carries
~1.1 k tokens of residual harness prompt — identical across arms, so it cannot
bias the comparison, but it inflates absolute figures and compresses relative
differences by adding a constant to both sides of every ratio.

**Arm A was reimplemented mid-experiment and its first 14 runs discarded.**
The first version accumulated screenshots in an append-only context, giving
the baseline caching the standard loop does not have. Those runs are archived
in `results/raw/discarded_armA_v1.jsonl` and excluded from every figure. If my
corrected baseline is wrong in some way I have not seen, every A figure moves.
Its history is textual: a baseline retaining the last 2–3 screenshots would be
a different and arguably stronger configuration, and was not measured.

**Compaction and crop-ageing were never exercised.** Tasks ran 7–10 steps;
both mechanisms need longer horizons. The 4× token disadvantage in §2.3 is
precisely what they exist to fix, so the tool arms are being reported without
the remedy for their main weakness. The crop-ageing parameter N could not be
studied at all.

**Uncovered changed regions are not detected** (DECISIONS D4.8). Arm C's
forced-crop rule fires on visual roles and on a failed bbox-honesty check, but
not on "a region changed with no tree element behind it". I hit this directly:
the first version of the vdelta tasks used plain `<div>`s, which Chromium does
not expose, and *neither* arm saw the rows. Adding ARIA roles made them
visible. Real applications with unexposed custom controls would blind both
tool arms in a way this suite now avoids by construction.

**Single environment, single model, single session.** One container, one
model, one provider, one day. Nothing here speaks to Electron or Qt
applications, other models, or applications with a poorer accessibility tree.
The instrumentation-coverage question that governs the whole economics of the
approach (§6.3 of the design document) was not measured at all.

## 5. What I would do next, in order

1. **Extend the verifier controls to the six browser tasks.**
   `tests/test_verifiers.py` now builds each task's correct end state and
   asserts the verifier accepts it, and asserts an untouched workspace is
   rejected — the guard whose absence let `calc_total` ship an unsatisfiable
   check that read as a hard task for the entire first version of this report
   (DECISIONS D6.1). It covers the twelve verifiers that read the filesystem.
   The six that read live page state over CDP are still uncovered, and two of
   them carry the sharpest result in the experiment.
2. **Measure how often the vdelta case actually occurs** in real task
   distributions. It is the whole justification for crop-priority and this
   experiment shows only that it exists, not that it is common.
3. **Exercise compaction and crop-ageing** on tasks of 30+ steps. The tool
   arms' one clear weakness — 4× total tokens — is exactly what these are for,
   and neither ran.
4. **Implement uncovered-region detection**, so that a changed region with no
   tree element behind it produces a crop instead of silence.
5. **Raise N to 10+ per cell and pin temperature** before treating any pooled
   success-rate comparison as meaningful.
6. **Measure instrumentation coverage** across a real application catalogue,
   including Electron with and without the accessibility flag.

## 6. Summary

The observation layer delivers its mechanical claims in full: visual grounding
failure becomes impossible rather than rare, pixel traffic falls ~6.5×, and
the prefix cache survives (91 % vs 22 %), worth ~380 ms/step.

Its economics are conditional. Under a tight cost budget the tool completes
2.3× as many tasks as the screenshot loop; with tokens unconstrained the two
are indistinguishable and the baseline uses 4× fewer raw tokens, because an
append-only context that is never compacted costs more to re-read than a short
context costs to rebuild. Which regime you are in decides whether to build
this.

The two structural findings are cleaner than the headline. **The advantage
comes from sending only what changed, not from having the element table**: arm
D has the table without the deltas and costs 3.1× more per completed task than
arm B, making it the worst option tested. And **crops are worth their tokens**:
they cost 3.4 % more image tokens across the suite, where they rarely
fire, and they are the difference between 6/6 and 0/6 when what changed is
visible but not describable.
