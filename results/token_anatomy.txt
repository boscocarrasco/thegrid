2. HOW THE TOTAL GROWS WITH STEPS
==========================================================================
  Fitting tokens_total = a + b*n and a + b*n + c*n^2 per arm,
  n = steps. R^2 says which shape the data actually has.

arm   n runs   tok/step   linear R2   quadratic R2         shape
A         62      2,418       0.999          1.000        linear
B         74      6,077       0.578          0.655     quadratic
C         74      6,768       0.489          0.489        linear
D         61     14,593       0.453          0.453        linear

  Pooling every task in one fit is a poor model for the tool arms:
  their per-step payload scales with the element table, which differs
  by an order of magnitude between a text editor and LibreOffice.
  Fitting *within* each task, where the table size is fixed, isolates
  the growth shape:

arm   tasks fitted   median linear R2   median quad R2  median gain
B                1              0.677            0.874        0.197
C                3              0.938            0.980        0.042

  An append-only arm re-reads its whole prefix every step, so its
  billed input is the sum of prefixes: quadratic in step count.
  An arm that rebuilds its transcript pays each prefix once: linear.

6. WHY A < B  (a screenshot every step, yet fewer tokens)
==========================================================================
                                         A           B      A/B
steps / task                          8.95       11.59     0.77
image tok / task                 10,992.58    1,695.51     6.48
obs tok / task                    1,373.15    5,504.59     0.25
cache_read / task                 3,687.26   75,124.42     0.05
cache_write / task               17,916.45    7,663.82     2.34
input (uncached) / task              17.90       23.22     0.77
total / task                     22,144.50   83,805.08     0.26
fresh / task                     18,457.24    8,680.66     2.13
cost / task                           0.08        0.06     1.40

  Gap in total:          61,661 tokens
  Gap in cache_read:     71,437 tokens (115.9% of the gap)

  Arm A rebuilds its transcript every step to drop the previous
  screenshot, so it never re-reads a prefix and its total stays
  linear. Arm B appends, so every step re-reads everything before
  it. The gap is almost entirely re-read tokens, which are the
  cheapest kind — which is why A's *cost* is higher despite this.
